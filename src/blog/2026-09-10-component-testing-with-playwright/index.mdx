Serenity/JS 3.47 brings web UI component testing into the same Screenplay Pattern architecture as the rest of your suite. The new `story` fixture mounts a Playwright component story and lets you turn its root into an Interaction Object with `Question.as(Constructor)`.

That means the component model you exercise in isolation can be the same one your end-to-end scenarios use in the running application. This release also introduces new guides to help you set up [component testing](/handbook/test-runners/playwright-test/component-testing/) and keep your web test code portable with [Serenity/JS web modules](/handbook/web-testing/serenity-js-web-modules/).

## Test components using the same language

A component test needs to mount a desired UI state, but it should not force you to abandon the Tasks, Questions, and Interaction Objects that make the rest of your test suite readable. If a component test uses raw locators while an end-to-end scenario uses a domain model, those tests duplicate both selectors and intent.

Serenity/JS 3.47 adds the [`story` fixture](/api/playwright-test/interface/SerenityFixtures/#story) to [`@serenity-js/playwright-test`](/api/playwright-test/). Give it the path of a component story and any serialisable props, then use `.as()` to construct an [Interaction Object](/handbook/web-testing/page-objects-pattern/#interaction-objects) around the mounted root:

```ts title="src/UserCard.spec.ts"
import { Ensure, equals } from '@serenity-js/assertions';
import { describe, it } from '@serenity-js/playwright-test';

import { UserCard } from './UserCard.serenity';

describe('UserCard', () => {
    it('displays the user name', async ({ actor, story }) => {
        const card = story('components/UserCard/Default', { name: 'Alice' })
            .as(UserCard);

        await actor.attemptsTo(
            Ensure.that(card.name(), equals('Alice')),
        );
    });
});
```

The fixture mounts the story only when the Actor first resolves it and keeps that mount for the test. The Interaction Object owns the selectors and UI mechanics; the scenario remains a description of the behaviour under test.

## Wrap Question answers in domain models

The [`story` fixture](/api/playwright-test/interface/SerenityFixtures/#story) builds on a new constructor overload of [`Question.as()`](/api/core/class/Question/#as) in [`@serenity-js/core`](/api/core/). `Question.as()` has long mapped an answer through a function. It can now also pass a resolved answer to a class constructor.

For example, a Question can transform a product ID with a mapping function or turn it into a domain model. In both cases, Serenity/JS resolves the original answer when the Actor needs it:

```ts title="spec/product-id.spec.ts"
import { Ensure, equals } from '@serenity-js/assertions';
import { actorCalled, Question } from '@serenity-js/core';

class ProductId {
    constructor(readonly value: string) {
    }
}

const productId = () =>
    Question.about('product ID', () => '42');

await actorCalled('Alice').attemptsTo(
    Ensure.that(productId().as(value => `product-${ value }`), equals('product-42')),
    Ensure.that(productId().as(ProductId).value, equals('42')),
);
```

The constructor form is what lets a mounted Page Element become an Interaction Object without special component-test plumbing. It also works wherever a Question answer needs a domain-specific wrapper, while preserving the composable `QuestionAdapter` API that Screenplay code relies on.

For Interaction Objects that need dependencies beyond their root Page Element, pass the `story(...)` result directly to the constructor instead. Serenity/JS resolves and mounts it when the Actor uses the object.

## Keep the same component model at every level

Testing a component in isolation should not create a second model of the same UI. When component tests use raw locators while integration scenarios use different Tasks and selectors, the two descriptions drift and a markup change can leave one level of the suite behind.

Serenity/JS gives you the tools and patterns to avoid that duplication: wrap the root of a mounted story in the same Interaction Object your integration tests use. The Interaction Object exposes the component's public, user-observable API as Questions and Tasks, while keeping selectors and UI mechanics inside the model.

Component tests then give fast feedback on the behaviour of a desired state, and integration scenarios confirm that the same model works with the running application. Because both levels exercise the same public API, they validate exactly the contract your end-to-end journeys depend on.

The new [component testing guide](/handbook/test-runners/playwright-test/component-testing/) shows how to create a story gallery, organise stories and Interaction Objects, and mount stories with the `story` fixture. It also explains when a focused browser-level contract is better served by Playwright's `mount` fixture and locators than by an Interaction Object.

## Make web behaviour portable too

Browser integration tools evolve, and a move from one to another should not force you to rewrite the user journeys your suite already describes. When Tasks, Questions, and Page Elements use a browser tool’s APIs directly, that migration spreads through the code that models your application instead of remaining a change to its browser integration layer.

[`@serenity-js/web`](/api/web/) separates those responsibilities. It provides portable Page Elements, web Interactions, Questions, and Expectations, while integration modules such as [`@serenity-js/playwright`](/api/playwright/) and [`@serenity-js/webdriverio`](/api/webdriverio/) give an Actor the concrete Ability to control a browser.

The choice of browser tool belongs where Actors receive their Abilities, not in test scenarios—and certainly not in the Tasks, Questions, or Page Element definitions that describe the application. That boundary lets the same sign-in or checkout Task serve a component test, an end-to-end scenario, or a synthetic check, and keeps that application-facing code largely unchanged as you change browser integrations.

The [Serenity/JS web modules guide](/handbook/web-testing/serenity-js-web-modules/) explains how to establish this boundary in your own suite.

## Getting started

If you use Playwright Test, start with the [component testing guide](/handbook/test-runners/playwright-test/component-testing/) and use the [`story` fixture](/api/playwright-test/interface/SerenityFixtures/#story) to mount a meaningful state of your component. Model interactions with the component using the [Interaction Object](/handbook/web-testing/page-objects-pattern/#interaction-objects) pattern, so the same Questions and Tasks work in component and integration tests.

If your suite spans more than one browser integration—or may need to migrate—read the [Serenity/JS web modules guide](/handbook/web-testing/serenity-js-web-modules/) to keep browser-tool choices at the Actor Ability boundary.

Enjoy Serenity! 🎉
